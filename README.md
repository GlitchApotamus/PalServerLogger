[![GitHub Release](https://img.shields.io/github/v/release/GlitchApotamus/PalServerLogger?style=flat-square)](https://github.com/GlitchApotamus/PalServerLogger/releases)
[![Auto Release](https://github.com/GlitchApotamus/PalServerLogger/actions/workflows/release.yml/badge.svg?branch=main)](https://github.com/GlitchApotamus/PalServerLogger/actions/workflows/release.yml)

PalServerLogger is a Windows-native DLL logging layer for Palworld servers. It captures console/debug output, persists session log files, and exposes the same stream over a websocket for bots, dashboards, and live monitoring tools.

The project is now split into modular source folders for runtime logic, logging, and console hook handling while keeping the same runtime behavior and packaging flow.

## What it does

- Captures output from Win32 console/debug APIs such as WriteConsole, WriteFile, and OutputDebugString
- Writes logs to per-session timestamped files under a dedicated app folder
- Keeps only the newest configured log files and removes older ones automatically
- Starts a websocket listener for live log streaming
- Authenticates websocket connections with a shared secret token
- Falls back to tailing likely log files when the normal console hook path is not available
- Auto-generates and repairs configuration files on first launch
- Uses a proxy loader to inject the logger automatically when the server launches

## Project layout

The current source tree is organized by responsibility:

- [src/dllmain.cpp](src/dllmain.cpp): DLL entry point and startup bootstrap
- [src/core/runtime.h](src/core/runtime.h) and [src/core/runtime.cpp](src/core/runtime.cpp): runtime state, config, websocket helpers, fallback log scanning, and shared logic
- [src/core/logging.h](src/core/logging.h) and [src/core/logging.cpp](src/core/logging.cpp): async file logging and log queue handling
- [src/hooks/console_hooks.h](src/hooks/console_hooks.h) and [src/hooks/console_hooks.cpp](src/hooks/console_hooks.cpp): MinHook-based console/debug interception
- [src/loader.cpp](src/loader.cpp): proxy loader that injects the logger
- [CMakeLists.txt](CMakeLists.txt): source-of-truth build definition for the logger and loader targets

## Installation

Place both generated DLLs into your Palworld server binaries folder, usually:

- Pal\Binaries\Win64\PalServerLogger.dll
- Pal\Binaries\Win64\d3d9.dll

On first startup, the runtime creates a dedicated folder named PalServerLogger and stores its config there.

The logger config path is:

- PalServerLogger\Config.json

This replaces the older legacy folder layout and will migrate older data automatically when the old path is detected.

## Runtime configuration

The logger generates a config file automatically on first launch. The current defaults are:

```json
{
  "max_log_files": 5,
  "timestamp_format": "%Y-%m-%d %H:%M:%S",
  "filename_timestamp_format": "%Y%m%d_%H%M%S",
  "websocket_enabled": true,
  "websocket_port": 8765,
  "websocket_host": "127.0.0.1",
  "websocket_secret": "<auto-generated on first startup>",
  "debug_hooks": false
}
```

### Configuration keys

- max_log_files: number of historical session logs to keep
- timestamp_format: format applied to log lines
- filename_timestamp_format: format used for generated file names
- websocket_enabled: enables or disables live websocket output
- websocket_port: local port for the websocket listener
- websocket_host: bind address for the socket listener
- websocket_secret: token required for websocket clients to connect
- debug_hooks: extra debug output for hook initialization and runtime behavior

If a config is missing supported fields, the logger fills in missing values without overwriting user values that are already valid.

## Loader configuration

The proxy loader also maintains a configuration file called d3d9_config.json in the same binaries directory. This controls which DLLs are loaded and the localizable text used by the loader.

Example:

```json
{
  "load_dlls": [
    "PalServerLogger.dll",
    "PalDefender.dll"
  ],
  "translations": {
    "ModThreadStarted": "Mod thread started.",
    "ConfigMissing": "Config missing. Generating default d3d9_config.json...",
    "DefaultConfigCreated": "Default config created.",
    "AttemptingLoad": "Attempting to load: {0}",
    "InjectedSuccess": "Injected {0}",
    "InjectedFailed": "Failed to inject {0}. Windows Error Code: {1}",
    "ConfigErrorMissingArray": "JSON does not contain 'load_dlls' array.",
    "ConfigErrorOpening": "Could not open config at: {0}"
  }
}
```

The loader only trusts the load_dlls array as the source of truth for injected DLLs.

## Websocket behavior

The logger starts a websocket listener on the configured host and port. By default, it binds to 127.0.0.1:8765 unless you change the values in Config.json.

Clients must provide the shared secret in one of these forms:

- Authorization: Bearer <token>
- ?token=<secret>

Connections without the correct secret are rejected. The logger suppresses exact duplicate lines during a cooldown period to avoid self-echo loops and keeps the stream cleaner for bots and dashboards.

Example payload:

```json
{"type":"log","message":"[2026-09-12 12:00:00] Server started"}
```

## Compatibility notes

This project is designed for native Windows server installs. It also includes fallback support for environment layouts where the server output is redirected or buffered differently, such as Wine, Proton, or AMP-based setups.

In those environments, console hooks may not capture the full stream consistently, so the fallback log-tail support watches likely game log files as a secondary path.

## Build from source

Requirements:

- CMake 3.20+
- Visual Studio/MSBuild on Windows
- C++17 toolchain

Build steps:

```powershell
cmake -S . -B build
cmake --build build --config Release
```

This produces the following artifacts in the build output:

- PalServerLogger.dll
- d3d9.dll
- packaged release zip when the post-build packaging step runs
